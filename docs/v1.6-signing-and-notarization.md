### Gap 1 — Windows binaries carry no VERSIONINFO ✅ *closed 2026-08-01*

> **As-built.** Four `build.rs` files (workspace root + each plugin crate) embed the
> resource via a `winresource` build-dependency declared under
> `[target.'cfg(windows)'.build-dependencies]`. For *build* dependencies that `cfg`
> resolves against the **host**, so the crate is only fetched when building on Windows
> and non-Windows builds are completely untouched (verified: 188 tests still green on
> macOS, no new compile time).
>
> Two decisions worth knowing:
>
> - **Failure warns, it does not abort.** There is no Windows toolchain here, so the
>   `rc.exe` call ships unverified, and a hard failure would break every Windows build
>   including the release job. What makes that safe is the new **`Verify Windows version
>   metadata`** step in `release.yml` (between `Collect artifacts` and checksum
>   generation): it reads `(Get-Item $exe).VersionInfo` for all four binaries and fails
>   the release if `ProductName != "Dofek"` or `FileVersion`/`CompanyName` is blank. A
>   silent build-script failure therefore cannot reach a release — it fails loudly at the
>   one point that matters. Same reasoning as PR 4's Job Object choice: prefer the
>   failure mode that can't strand a release.
> - **`ProductVersion` tracks each crate, not the app release.** The plugins version
>   independently (0.1.x against dofek's 1.5.x) and a plugin's build script has no honest
>   way to learn the app version. SignPath needs one consistent `ProductName` with
>   versions present, which this satisfies; components of a signed suite routinely carry
>   their own versions. `ProductName` is `"Dofek"` on all four, matching Tauri's
>   `productName`; `FileDescription` and `OriginalFilename` distinguish them.
>
> **Still unverified:** the resource has never been compiled. First Windows CI run will
> either produce the metadata or fail the new assertion — either outcome is informative,
> neither is silent.

<details><summary>Original finding</summary>

There is no `build.rs` anywhere in the workspace and no `winres`/`winresource`
dependency. Only the GUI exe and MSI get product name and version metadata, because
`tauri-build` embeds them. `dofek-tui.exe`, `dofek-ollama.exe`, `dofek-docker.exe`, and
`dofek-net-ping.exe` ship with **no ProductName, no FileVersion, no CompanyName**.

SignPath's terms require metadata set "consistently across all signed binaries", and an
Authenticode signature on a resource-less exe also gives Explorer nothing to show in the
Digital Signatures tab.

**Fix (the one piece of code this track needs, ~15 lines × 4 crates):** add a
`winresource` build script to `dofek` (for the `dofek-tui` bin) and to each of the three
plugin crates, gated on `cfg(windows)`, populating `ProductName`, `FileVersion`,
`ProductVersion`, `CompanyName`, `LegalCopyright`, and `FileDescription` from the
existing Cargo metadata. Values must match what Tauri already writes for the GUI
(`bundle.publisher = "Asaf Saar"`, `bundle.copyright = "Copyright (c) 2026 Asaf Saar"`).

Do this **before** submitting — the reviewer downloads and inspects the current release
artifacts, and the mismatch is visible in one right-click.

</details>

### 1.2 What the certificate actually is

The certificate is issued to **SignPath Foundation**, not to Asaf Saar. Consequences,
so there are no surprises later:

- Windows shows the publisher as "SignPath Foundation" in the UAC/SmartScreen prompt.
- SmartScreen reputation accrues to that shared certificate. Reputation is inherited
  from other Foundation-signed projects rather than built from zero — usually a win, but
  it is not under dofek's control.
- Every signing request needs manual approval in the SignPath web UI per release. This
  is not automatable and is deliberate.
- The Foundation can revoke if the project stops meeting the conditions.

If dofek ever gains a proprietary component or a commercial dual-license, this track
dies and the fallback below applies.

### 1.4 After approval — CI integration

1. Create the SignPath project + a signing policy ("release-signing"), and register
   GitHub Actions as the trusted build system with this repo as the origin.
2. Add repo secrets: `SIGNPATH_API_TOKEN`, `SIGNPATH_ORGANIZATION_ID`.
3. Insert the signing step into `release.yml`'s **`build-windows`** job **between**
   `Collect artifacts` (line 65) and `Generate SHA256 checksums` (line 99) — so
   `SHA256SUMS.txt` covers the *signed* bytes. This ordering is the whole point;
   getting it backwards ships checksums that never match what users download.
4. The signing round-trip includes a human approval step, so the job will block. Give
   that step a generous `timeout-minutes` and expect the release run to sit waiting.

### 1.5 Fallback if SignPath declines

Azure **Artifact Signing** (formerly Trusted Signing), ~$120/yr — but check eligibility
*before* counting on it, because it moved to GA in April 2026 with a hard geographic
split:

- **Individual** sign-up: United States and Canada only.
- **Organization**: US, Canada, EU, UK, Australia, New Zealand, Japan, South Korea,
  Singapore, Switzerland, Norway, Israel.

An individual outside the US/Canada cannot sign up at all, so for most of the world the
fallback is really "enroll a legal entity" or "buy a conventional OV certificate from a
CA" (~$200–400/yr, hardware-token delivery, and a from-scratch SmartScreen reputation
climb). Determine which bucket applies before assuming this fallback exists.

## 2. Track B — macOS (Apple Developer Program)

### 2.1 Enrollment decision — Individual vs Organization

| | Individual | Organization |
|---|---|---|
| Requires | Apple ID with 2FA, credit card | D-U-N-S number, legal entity, authority-to-bind verification |
| Latency | usually 24–48 h | 1–4 weeks |
| Gatekeeper shows | your legal name | company name |

**Recommendation: Individual.** dofek's copyright and Tauri `bundle.publisher` are
already "Asaf Saar", the repo is personal, and Organization adds weeks of D-U-N-S
paperwork for a cosmetic difference. Switching later is possible but means re-issuing
certificates and re-notarizing.

Enroll at <https://developer.apple.com/programs/enroll/>. $99/yr, auto-renewing —
**a lapsed membership invalidates the Developer ID certificate and every future
notarization**, so put the renewal date in a calendar.

### 2.2 Certificates and credentials to create

1. **Developer ID Application** — this is the one that matters. Signs `.app`, the
   sidecar, the standalone TUI, and the three plugin binaries.
2. **Developer ID Installer** — **not needed.** dofek ships `.dmg` + `.app.zip`, no
   `.pkg`. Skip it.
3. **App Store Connect API key** for `notarytool` (Keys tab → Developer ID role).
   Prefer this over an app-specific password: it is not coupled to Apple ID 2FA, does
   not break when the account password changes, and is independently revocable.

Export the Developer ID Application cert + private key as `.p12`, then base64 it for
CI. Store both the `.p12` and its password in a password manager — losing the private
key means re-issuing and re-notarizing everything.

Repo secrets:

```
APPLE_CERTIFICATE           base64 of the .p12
APPLE_CERTIFICATE_PASSWORD  the .p12 export password
APPLE_SIGNING_IDENTITY      "Developer ID Application: <Name> (<TEAMID>)"
APPLE_API_KEY               the Key ID
APPLE_API_ISSUER            the Issuer ID (UUID)
APPLE_API_KEY_PATH          path written at runtime from a base64'd .p8 secret
APPLE_TEAM_ID               10-char team identifier
```

### 2.3 What Tauri does for free, and what it does not

With `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGNING_IDENTITY` and the
`APPLE_API_*` trio present, `cargo tauri build` (release.yml:277) signs the `.app` with
hardened runtime, signs the `externalBin` sidecar (`dofek-tui`) inside the bundle,
notarizes, and staples the `.dmg`. **No workflow change is needed for the GUI path**
beyond exposing the env vars.

Not covered, and needing explicit steps in the `build-macos` job between the artifact
collection (line 281) and the checksum generation (line 327):

- `dofek-tui-aarch64-apple-darwin` (the standalone download, line 289)
- `dofek-ollama` / `dofek-docker` / `dofek-net-ping` (line 298)

For each:

```bash
codesign --force --options runtime --timestamp \
         --sign "$APPLE_SIGNING_IDENTITY" "$binary"
```

then notarize as a batch — `notarytool` takes a zip, and a **bare Mach-O binary cannot
be stapled**, so there is no `stapler` step for these four:

```bash
ditto -c -k --keepParent artifacts notarize.zip   # or zip the four binaries
xcrun notarytool submit notarize.zip \
      --key "$APPLE_API_KEY_PATH" --key-id "$APPLE_API_KEY" \
      --issuer "$APPLE_API_ISSUER" --wait
```

Gatekeeper checks the notarization online on first run. That is fine for CLI binaries;
the offline-launch case is exactly why the `.app`/`.dmg` path *is* stapled.

Verify locally before believing CI: `codesign -dv --verbose=4 <binary>` and
`spctl -a -vvv -t install <dmg>`.

## 3. Ordering traps

1. **Sign before checksums.** Windows: insert between release.yml:65 and :99. macOS:
   between :281 and :327. The combined manifest at :378 concatenates the per-platform
   files, so if each platform is correct the combined one is too.
2. **SignPath modifies the MSI after bundling.** Any signature computed over pre-signing
   bytes is invalid. This is the trap that bites v1.7's auto-update: the updater's
   minisign `.sig` is computed over the *final* artifact, so `cargo tauri signer sign`
   must run **after** the Authenticode step, not as part of the Tauri build.
3. **Notarization is asynchronous.** `--wait` can take several minutes and occasionally
   much longer during Apple outages. Do not add a tight step timeout.
4. **Apple membership lapse silently breaks releases.** The build succeeds; the
   notarization request is what fails.
